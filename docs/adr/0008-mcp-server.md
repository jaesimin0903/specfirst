# ADR 0008: An MCP server for agents that move money (`@specfirst/mcp`)

Date: 2026-10-08. Status: accepted. Read only; nothing deployed. Revised the same day after review: the verdict rests on the verified report file rather than on the API's summary of it, proceed needs the issuer and the implementation read and matching, links and CCIP-Read cannot send a read to another host, deposit and mint count the exits only when both are broken, and text from the vault is quoted on one line. A second review the same day: proceed also needs the check to have run at full strength (the pinned suite, 16 fuzz runs or more, delta 0, the suite hash the API names), an answer of either source this code cannot use degrades to caution instead of a tool error, names are JSON-quoted with bidi and zero-width characters removed, feed events are held to their shapes one by one, `recent_findings` has one deadline, and the API base must be an origin.

## Problem
The callers that rely most on what a vault says about itself are the ones with no person in the loop: yield bots and AI agents that size deposits and withdrawals from `maxWithdraw` and the previews. Upshift earnAUSD answers `maxWithdraw` with the whole balance while every withdraw reverts; an agent that trusts the answer gets stuck. Specfirst already knows this (the board, the API of ADR 0005, the registry of ADR 0004, the watcher of ADR 0006), but an agent would have to know our routes, read a report, tell a MUST from a SHOULD, and check the registry itself. Agents are increasingly wired to tools through the Model Context Protocol, so the natural interface is an MCP server whose answer to "may I move money here" is one word with reasons.

## Decision
A workspace package, `packages/mcp` (`@specfirst/mcp`, MIT), built on the official MCP TypeScript SDK at its current stable line, v2 (`@modelcontextprotocol/server` 2.3, zod 4 for the tool schemas), served over stdio with `serveStdio`, the transport Claude Code and Claude Desktop launch. `serveStdio` serves a client that opens with a 2025 `initialize` as a 2025-era server, so older hosts work too. The bin is `specfirst-mcp` (`dist/index.js`).

Four tools, read only and few on purpose:

| Tool | Answers |
|---|---|
| `check_before_moving_funds` {address, chainId = 143, action: deposit, mint, withdraw or redeem, amount?} | refuse, caution or proceed, with coded reasons and which max function not to size from |
| `vault_verdict` {address, chainId = 143} | status, level (must, rounding, should, none), each failure with its EIP-4626 sentence, a plain explanation and the concrete call, traits, the block and its age, the report URL, and the latest attestation read on chain |
| `recent_findings` {chainId = 143, limit = 10} | the watcher's result changes and confirmed share value falls, newest first, and the vaults whose latest check is a mismatch |
| `how_to_watch` {address, chainId = 143} | CheckSubscriptions with its fee per day read on chain, the subscribe call, the inbox and the webhook kinds; informational |

Mint is an action next to the three the plan named because it is an ERC-4626 entry point with its own max function.

### Two sources, read separately
- The Specfirst web API (`SPECFIRST_API_BASE`): `GET /api/v1/vaults/<chainId>/<address>` (the latest report summary and the web's own attestation read), the report file it links, and `/api/v1/watch/{feed,status,vaults}`. The web is not changed: what the vault route lacks (the rounding level, the traits, the concrete calls) is read from the report file. A link the API returns is followed only as an http(s) path on the configured base, and only when the result has the base's origin, so the API cannot send a read elsewhere.
- `CheckAttestationRegistry` on Monad testnet (`MONAD_TESTNET_RPC`), read by this process with viem and core's bundled ABI: `latest`, `isCompliant` and `isIssuer` of the attesting issuer, after checking that the RPC's `eth_chainId` is 10143 (a mainnet RPC would answer "no attestation" for everything). `NoAttestation` is "none"; any other failure, and no answer within twice the request timeout, is "unread", never "none". CCIP-Read is off: an RPC that answers with an `OffchainLookup` revert cannot make this process fetch a URL of its choosing.
- The report file is held to core's `standardCheckReportSchema` (which also checks its summary against its results), and its keccak256 over its canonical JSON (`checkReportHash` of core, the hash the registry records) is computed here. A file that does not hash to the reportHash the API names, or is about another chain, vault or block, is not used. A file that is used is what the verdict rests on: status, counts and failures come from its results, and an API summary that disagrees with it is reported and blocks proceed. The attestation is compared with that hash (`matchesReport`) and with the report's implementation key (`sameImplementationAsReport`).

### Levels
A failure's level is read the way the board reads it (`packages/web/lib/board/levels.ts`): the level and EIP sentence of each property from core's `ERC4626_PROPERTY_LEVELS`, withdraw and redeem failures always MUSTs, and a round trip shown as rounding only when every value pair in its logs is within max(2 base units, 1 bp). The web keeps that module free of imports and does not export it, so the package carries the rounding rule and a test runs both on the same inputs.

### The decision
Refuse needs evidence, proceed needs evidence, and everything in between is caution; nothing that fails to load leads to proceed.
- A property concerns an action when it is about that entry point; the four accounting views concern every action; an id outside the table concerns everything. Money that goes in has to come out, so for deposit and mint the exits count too, but only when both withdraw and redeem fail a MUST: with one of them working the money can come out through it, which is a caution (`one-exit-broken`).
- Refuse: a MUST failure that concerns the action in the latest report, or in the registry's latest Valid, non-compliant attestation about the same implementation, counting only bits of the 30-property table. The on-chain answer wins over a newer, unattested report that passes: until a check is attested, the registry is what a contract reading it would act on. An attestation of code the vault no longer runs is a caution, not a refusal; a bit outside the table means another property table, also a caution.
- Caution: a MUST that does not concern the action, one broken exit for deposit and mint, SHOULD-only or rounding failures, properties not judged or not applicable, an unchecked vault, the API or the report unreadable, unusable or not hashing, a check older than `SPECFIRST_MCP_STALE_HOURS` (48, twice the watcher's sweep) or of an unknown or future time, asynchronous redemption, no attestation, a revoked one, a non-compliant one without a MUST for the action, the registry unread, a removed or unread issuer, an attestation of another or an unknown implementation. With the API down only a Valid attestation stands in for the report.
- Proceed: the verified file has exactly the 30 properties of a published table, all passed, ran at full strength (the pinned upstream commit, at least 16 fuzz runs, delta 0, and `suiteHash(suiteOf(report))` equal to the API's suiteHash; the attested suite hash cannot be required, since the attestation is often of an earlier check under an earlier harness), agrees with the API's summary and is fresh, and the registry's latest attestation is Valid, compliant, with 30 passes and an empty bitmap, from an issuer read and still current, about the same implementation. The attestation may be of an earlier check with the same outcome: the watcher does not attest unchanged results (ADR 0006), so the latest attestation of a healthy vault is usually older than its latest report, and requiring a match would turn every healthy vault into caution.
- The amount is echoed and does not move the decision: a check tries the vault's own max values for test users at one block, not the agent's amount.
- Every result says that a pass is "no counterexample found at that block", not a safety guarantee, and that a mismatch is not a claim of loss of funds.

## Trust model
The server holds no key, builds no wallet, and sends only GETs, `eth_chainId` and `eth_call`. Vault names, symbols and revert texts are the vault's and its deployer's words: they are cleaned to one bounded line and quoted, and the server's instructions tell the agent to act on the decision and the reason codes. It adds nothing to what ADR 0004 says an attestation means: a reader of the registry trusts its issuers. What it does add is that an agent need not trust our web for the on-chain part: with the API down, the registry alone still refuses a MUST and never proceeds; with the RPC down, a passing report alone never proceeds.

## What it does not guarantee
- That a vault is safe. A result is about one block and the 30 properties; a vault that behaves differently off a fork is not caught.
- Freshness beyond the stale limit: the watcher re-checks known vaults about daily, so a vault can change for up to a day before any result does.
- That the web serves its latest report: the hash check catches an altered file, not an omitted newer one. The registry read narrows that gap for the vaults that are attested.
- `recent_findings` reads at most the last 1,000 feed events; a vault whose latest check is older does not appear in its mismatch list.

## Evidence
- `packages/mcp/test` (vitest, 115 tests): the decision rules on fixtures captured from the live web and registry on 2026-10-08 (Upshift earnAUSD MUST, tyYIELD rounding, a MetaMorpho vault all passed) and their variations, with a sweep that no vault and no action proceeds when a source is down, stale or unattested; the level rules against the board's own module; the API client and the chain reader against local mocks, a dead port, an RPC of the wrong chain, links with other hosts or schemes, a body over 4 MiB, an answer of the wrong shape, and an `OffchainLookup` revert that a default viem client follows and this one does not; the feed reading with paging and its cap; that no source file reads a key or signs; and an end to end run of `dist/index.js` over stdio with the SDK client against a mocked API and RPC, including a host that opens with a 2025-06-18 `initialize`, the API down and the RPC down, with the traffic checked for GETs and `eth_call` only.
- Live, read only, against the local web and the public testnet RPC on 2026-10-08: Upshift withdraw, redeem and deposit refused on `sf-maxWithdraw-honored` and `sf-maxRedeem-honored` (both exits) with attestation #15 read on chain; tyYIELD caution (rounding only, attestation #24 of the same report); Steakhouse High Yield USDC `0x802c..4e44` proceed (30 of 30 at block 111209140, attestation #17 compliant, of the earlier block 109195820, same implementation); an unknown address caution with the desk link; CheckSubscriptions at 0.05 MON a day.
