# ADR 0005: Paid check requests (`CheckRequestDesk`) and the unattended worker

Date: 2026-09-30. Status: accepted and deployed on Monad testnet at `0x4de46c70cB77C5Fcbe083C436bb42F097CBFafeb` on 2026-10-01; the first two real requests were fulfilled. Revised 2026-10-01 after code review: the worker reuses its own attestation instead of attesting twice, counts only reverts toward a refund, re-reads a request before attesting, classifies pre-check errors positively, caps reject gas and takes a lock on its directory. Revised 2026-10-06 after a second review, the worker only: a subject RPC failure never refunds, a report with fork RPC errors is not attested, each check has a time budget, an attestation of any allowed issuer that checked the subject as of the request delivers it (OlderThanLatest is not a failure), the attest transaction is journaled before its receipt, and the worker stops when it is no longer the desk's worker. The contract did not change.

## Problem
Every attestation in `CheckAttestationRegistry` (ADR 0004) so far was made by hand: someone runs `specfirst check <vault>`, then `specfirst cert attest <report>`. Nobody outside the project can ask for a check, and the work earns nothing. For the demo the loop has to close without us: a user pays a fee in testnet MON to have a vault checked, a worker checks it, records the attestation and delivers, and the fee becomes ours only once the check is delivered. If we deliver nothing, the user gets the fee back.

## Decision
A new contract, `packages/contracts/src/CheckRequestDesk.sol` (MIT), next to `CheckAttestationRegistry`, which does not change. The web builds on this interface, so it is fixed for the first deployment:

    enum RequestStatus { None, Pending, Fulfilled, Rejected, Refunded }
    struct Request { address requester; uint64 subjectChainId; address subject; bytes32 standardId; uint96 fee;
                     uint64 requestedAt; RequestStatus status; uint256 attestationId; bytes32 rejectReason; }
    constructor(address owner, address worker, address registry, uint96 fee, uint64 timeout)
    requestCheck(subjectChainId, subject, standardId) payable returns (id)     anyone, msg.value == fee
    fulfill(id, attestationId)                                                  worker, Pending only
    reject(id, reasonCode)                                                      worker, Pending only, full refund
    refundExpired(id)                                                           anyone, Pending and timed out
    withdraw(to)                                                                owner, earned - withdrawn only
    setFee(fee), setWorker(worker)                                              owner
    views: requestOf(id), requestCount(), fee(), worker(), owner(), registry(), timeout(), earned(), withdrawn(), escrowed()
    events: CheckRequested, CheckFulfilled, CheckRejected, CheckRefunded, FeesWithdrawn, FeeSet, WorkerSet

- Request ids are the zero based index of one list: valid ids are `0 .. requestCount() - 1`, like attestation ids. `requestOf` of any other id reverts with `UnknownRequest(id)`.
- `standardId` is `keccak256(bytes(standard))`, the registry's key. `requestCheck` refuses a zero subject, chain id or standardId.
- The constructor parameters are named `owner_`, `worker_`, ... in the source so they do not shadow the getters; the ABI types and order are the ones above.

### Fee escrow
- `requestCheck` takes exactly `fee` (`WrongFee(sent, fee)` otherwise) and stores it in the request; a later `setFee` changes only new requests. The fee is added to `escrowed`, the sum of the fees of Pending requests.
- `earned` grows only in `fulfill`, by that request's fee. `withdraw(to)` pays `earned - withdrawn` and reverts with `NothingToWithdraw` at zero, so the owner can never reach an escrowed fee.
- Without forced transfers the balance is exactly `escrowed + earned - withdrawn`. The desk has no receive or fallback function; coins forced in with selfdestruct or as a coinbase stay locked (nothing pays them out).

### Fulfill: the registry is the evidence
`fulfill(id, attestationId)` reads `registry.attestationOf(attestationId)` and requires, in this order:
1. the attestation exists (`attestationId < registry.attestationCount()`, else `UnknownAttestation`);
2. it is about the request's `subjectChainId`, `subject` and `standardId` (`AttestationMismatch`);
3. it was issued at or after the request: `issuedAt >= requestedAt`, both block timestamps in seconds (`AttestationBeforeRequest`), so an old attestation cannot be passed off as the delivery;
4. it is not Revoked (`AttestationRevoked`). A Superseded attestation is accepted: a later check of the same subject does not undo a delivery that was valid.

The attestation's result does not matter: the user pays for a check, not for a pass, so a report with failures or inconclusive properties is delivered like any other. One attestation may close several requests for the same subject made before it. Timestamps have a resolution of one second and Monad blocks are faster, so an attestation from an earlier block of the same second counts as issued at the request. The contract only compares issuedAt, which says when the attestation was sent, not which state it checked: an attestation sent after the request can still be of a check that forked before it (the check of an earlier request for the same vault, the same second or minutes later), and one made by hand with the worker's key passes too. The worker therefore delivers by a stricter rule of its own (`canDeliver`, below): the attestation's subject block must be from at or after the request, unless it is the attestation of this request's own report.

### Two refund paths
- `reject(id, reasonCode)`: the worker closes the request without a check and the whole fee goes back to the requester in the same transaction. `reasonCode` is a short ASCII code right padded with zeros into a bytes32 (not a hash); the worker's codes are exported as `REJECT_REASONS` from `@specfirst/core`: `not-erc4626`, `check-failed`, `unsupported-chain`, `unsupported-standard`, `unknown-proxy`, `attest-failed`, `fulfill-failed`.
- `refundExpired(id)`: anyone, once `block.timestamp >= requestedAt + timeout` (seconds; `NotExpired(id, expiresAt)` before), pays the fee to the requester, not to the caller. This is the user's protection when the worker is down or stuck. The worker may still fulfill a timed-out request until someone refunds it.
- A requester that refuses coins (a contract without a payable receive) cannot be refunded: both paths revert with `TransferFailed` and the fee stays escrowed until the request is fulfilled. Pull payments would avoid that but add a claim step and state to the interface the web already builds on; requests come from wallets through the web, so the desk pushes.

### Roles, transfers, reentrancy
- The owner is set by the constructor and is immutable (no transfer, no renounce), as in the registry. It sets the fee and the worker and withdraws earned fees. If its key is lost, fee and worker are frozen and a new desk is deployed. `registry` and `timeout` are immutable too.
- Coins leave only through `call`, after every state change, and a failed call reverts (`TransferFailed`). `requestCheck`, `fulfill`, `reject`, `refundExpired` and `withdraw` share a reentrancy lock (a storage flag, not transient storage, so nothing depends on the chain's TSTORE support). Tests re-enter from a refund into another refund and into `requestCheck`, and from a payout into `withdraw`; each nested call gets `Reentrancy`.

## Worker trust model
Can the worker take a fee with a fake attestation? Yes, and the desk cannot stop it. The worker signs with `ISSUER_PRIVATE_KEY`, the same key that is an issuer of the registry, and an issuer can attest any values for any subject (ADR 0004: the registry cannot read the subject chain). A dishonest or stolen worker key can attest a subject without running the suite, then fulfill with that attestation and earn the fee. What the desk does guarantee:
- the fee is earned only against an attestation that exists, names the requested subject, chain and standard, is newer than the request and is not revoked; the worker cannot fulfill with someone else's old attestation or with an attestation about another contract;
- the worker cannot withdraw (owner only), cannot redirect refunds (they go to the requester), and cannot touch escrowed fees except by fulfilling or rejecting their own request;
- every attestation can be rechecked by anyone (ADR 0004: reportURI, reportHash, suiteHash, seed, block), so a fake one is provable after the fact; the owner can `setWorker` to a new key and the registry owner can remove the issuer.

A revocation after the fact does not return the fee: fulfill is final. The desk does not ask who issued the attestation: after `setWorker`, attestations of the previous worker still fulfill, and so do attestations of any other issuer. The worker itself delivers an attestation of another issuer (the watcher's, ADR 0006) only while the registry still lists that issuer and only under `canDeliver`. Splitting the worker key from the issuer key does not help while one operator holds both. Real separation needs an independent attester or a challenge window (below), which is out of scope for the first deployment.

## The worker (`specfirst worker`)
- Signs with `ISSUER_PRIVATE_KEY`. At start it refuses to run unless that address is `desk.worker()` and an issuer of `desk.registry()`; the registry is read from the desk, not from the environment. Writes go through the guarded wallet: monad-mainnet is refused before a key is read, the wallet refuses chain 143, and each RPC's `eth_chainId` is checked before its first transaction.
- It serves one subject chain: the chain of `--subject-rpc` (read only; default Monad mainnet from `MONAD_MAINNET_RPC` or the public RPC). Requests for any other chain are rejected with `unsupported-chain`, other standards with `unsupported-standard`.
- It reads requests with `requestCount()` and `requestOf(i)` from a cursor, not from event logs: the testnet caps `eth_getLogs` at 100 blocks and the public RPC allows about 15 requests per second. Every id below the cursor is closed onchain or given up, so a pass costs one read plus one per open request.
- Requests are handled one at a time in id order. At the start of every pass, and again right before each attest, the worker reads `desk.worker()`; when it is another address (`setWorker`), the pass stops with `WorkerReplacedError` (exit 18 with `--once`) and nothing is attested, fulfilled or rejected until it is the worker again. A fulfill or reject that reverts with `NotWorker` stops the pass the same way and counts nothing.
- Delivery (`canDeliver`). For a Pending request the worker first reads the registry's latest attestation of the subject, chain and standard, whoever issued it. It delivers the request, and the worker fulfills with it without a check (event `worker-reused`, with the issuer), when it is Valid, was issued at or after the request (the desk's own rule) and checked the subject as of the request: the timestamp of its subject chain block is at or after `requestedAt`, or it is the attestation this worker made from this request's own saved report (same issuer and reportURI, whatever its block). Another issuer's attestation counts only while the registry still lists that issuer. The same look is taken again right before attesting and before any reject, so a check of the watcher, a crash after an attest was mined, or a second request for a vault just checked all end in a fulfill instead of a second attestation or a refund. A check that forked before a later request does not deliver that request: it gets its own check.
- The check. A check starts only while the request has the check budget plus a margin left before `requestedAt + timeout` (600 + 300 s; the desk's clock is the timestamp of its latest block); a request with less is rejected with `check-failed` ("not checked: the request times out in N s") instead of starting a check that a `refundExpired` could overtake. Then: pre-check the subject at `latest - --block-lag` (default 10) blocks (code, `asset()` a non-zero address, `totalAssets()`; only an answer from the contract, a revert, no data or data that does not decode, means `not-erc4626`); run `runStandardCheck` at that block within the budget (30 properties, `--runs` default 16, report under `.specfirst/checks` as `specfirst check` writes it); copy the report to `certs/checks/<chainId>/<address>/<block>-<hash8>.json` (the `cert attest` rule); check the subject's identity on its chain (`verifySubjectCode`); read the request again (a request refunded during the check is not attested), read `desk.worker()` and look for a delivering attestation once more; attest; fulfill. An unresolved proxy is rejected with `unknown-proxy` unless `--allow-unknown-proxy`.
- A subject RPC failure is never a verdict. The pre-check, the check and the identity check get 3 attempts within a pass (5 s and 20 s apart). When the last one failed on the subject chain's RPC (a transport failure, a rate limit, a node error, a JSON-RPC server error, or forge failing to fork, a 429 in its output included), the request stays open with `retryAt` in state.json, the wait doubling from 30 s up to 10 minutes, and is tried again in later passes until the time rule above rejects it. Only a contract answer (`not-erc4626`), an identity mismatch, an unknown proxy or a check that fails on its own (forge failing for another reason, after its 3 attempts) rejects at once. Before, 3 failed attempts (about 25 s) rejected and refunded: an outage of the subject RPC refunded every request it touched.
- Fork RPC errors. A report with any property left inconclusive by a fork RPC error (`forkRpcErrorsOf`) says more about the RPC than about the vault: it is not saved under `certs/checks` and not attested, and the request is checked again after 5 minutes times the runs so far. After 3 such runs it is rejected with `check-failed`. The watcher treats these reports the same way.
- Check budget (`--check-timeout`, 600 s): one budget per request's check, shared by its attempts within the pass (a retry gets what the earlier attempts left). A check that runs out is not retried: the request is rejected with `check-failed`, and the subject goes into `timedOut` in state.json; its requests in the next 24 hours are rejected without a check, and after that it is checked normally again. Why reject rather than deliver a check that records the timeout: a stopped forge leaves no report (`runStandardCheck` throws, no results, seed or sender come back), so the existing report and attest path cannot represent it; a made-up report with all 30 properties inconclusive would supersede the subject's last meaningful attestation in the registry and set off the watcher's change alerts; and the worker cannot tell a vault that burns its time from a slow fork RPC, for which a refund is the honest outcome. The refund is not a cheap way to stall the worker: a stall costs at most one budget per request (no retries, where before one request could hold the worker for 3 times an hour), and stalling it again with the same vault is refused for a day, so each further stall needs a new contract on the subject chain. Reruns after fork RPC errors are bounded the same way, at 3 runs of one budget each.
- Transactions. A failing attest, fulfill or reject is retried in the next passes; only reverts (a decoded contract error or a reverted transaction) count, and after 3 counted failures in a row the request is rejected with `attest-failed` or `fulfill-failed` (refund) or, for a reject that keeps reverting, given up (the requester can still `refundExpired`). RPC outages, rate limits and receipts that do not arrive never count, so a short outage never becomes a refund. An attest that reverts with `OlderThanLatest` is not a failure: another issuer attested a later block of the subject while the check ran. When that attestation delivers the request (`canDeliver`) the worker fulfills with it; otherwise it drops the saved report and checks again at a new block, at most 3 checks in all.
- Attest journal. The attest transaction's nonce is fixed before sending (the pending count, passed explicitly), and its hash and nonce are written to state.json (`attestTx`) as soon as the node accepts it, before the receipt is awaited. A pass that finds a journal looks the transaction up before anything else: mined, its attestation is the request's; reverted, it counts like a revert; pending, the worker waits; unknown to the node, it is sent again with the same nonce while that nonce is unused (so at most one of the two can be mined), and otherwise the request goes on and finds the attestation of its own report if one landed. A crash between sending and writing the journal is covered by the own-report rule of `canDeliver`.
- Any other error of a request (a report that cannot be written, for example) is recorded and retried, and after 3 passes in a row the request is rejected with `check-failed`; RPC failures, JSON-RPC server errors (-32603 and -32000 to -32099) included, never count. A request with a decided reject still looks for a delivering attestation before the reject is sent. A request refunded by someone else while it waits is noticed and not checked; given-up requests are read again each pass so their status follows a later refund.
- A reject whose gas estimate is above 300,000 gas is not sent and the request is given up at once: a requester contract whose receive function burns gas would otherwise make each refund expensive for the worker. Such a requester refunds itself with `refundExpired`. The desk forwards all gas on refunds on purpose, so smart contract wallets can receive them.
- The worker takes `.specfirst/worker/worker.lock` (its pid, created exclusively) and refuses to start while another live worker holds it; a lock left by a dead process is taken over. Two workers on one state directory would attest twice and race on nonces. Known gap: the lock is per project directory, not per (chain, worker address), and the takeover of a stale lock is not atomic, so two workers started from two directories with one key are not stopped; the operator runs one.
- `reportURI` is `<base>/<chainId>/<address>/<block>-<hash8>.json` with base `--report-base-url`, else `SPECFIRST_REPORT_BASE_URL`, else `https://raw.githubusercontent.com/jaesimin/specfirst/main/certs/checks`. The worker writes the copy locally; with the default base the URI resolves only once `certs/checks` is committed and pushed, which stays an operator step.
- Files, both in `.specfirst/worker/` of `--project`:
  - `state.json`: `{ version: 1, desk, chainId, cursor, requests: { "<id>": { failures, block?, reportPath?, reportURI?, attestTx?: { hash, nonce }, attestationId?, reject?, detail?, gaveUp?, retryAt?, deferrals?, checkRuns? } }, timedOut?: { "<subject>": { at, block } } }`. It keeps the saved report, the sent attest and the attestation id of unfinished requests, so a restart resumes at the failed step instead of paying for the check again or attesting twice; `retryAt` holds a request back after a subject RPC failure (`deferrals` in a row set the wait) or between reruns, `checkRuns` counts checks that could not be attested. A state.json of another desk or chain is refused. The added fields are optional, so a state.json of the 2026-10-01 worker loads unchanged; that worker refuses a state.json that uses them.
  - `status.json`, for the web: a flat object with the request ids (decimal strings) and one `totals` key side by side: `{ "<id>": { stage, updatedAt, block?, reportPath?, attestationId?, txs: { attest?, fulfill?, reject? }, gasCostWei?, error? }, "totals": { gasCostWei, fulfilled, rejected } }`. `stage` is `queued`, `prechecking`, `running`, `attesting`, `fulfilling`, `fulfilled` or `rejected`; big numbers are decimal strings; `gasCostWei` is gasUsed times effectiveGasPrice over the request's transactions; totals are recomputed from the entries on every write. The zod schema is `workerStatusSchema` in `@specfirst/core/desk`, a browser-safe subpath (viem and zod only).
- Logs are NDJSON events with `--json` (`worker-start`, `worker-pass`, `worker-stage`, `worker-retry`, `worker-step-failed`, `worker-deferred` (a request held back until `retryAt`), `worker-fulfilled`, `worker-rejected`, `worker-closed`, `worker-reused` (with the issuer), `worker-gave-up`, `worker-error`, `worker-pass-done`, plus the `check-*` events of the suite). The loop never stops on a failed pass; `--once` runs one pass and exits.

### CLI

    specfirst desk deploy [--network monad-testnet|anvil] [--rpc <url>] [--registry-attest <address>] [--worker <address>] [--fee <MON>] [--timeout <sec>]
    specfirst desk request <address> [--subject-chain 143] [--standard erc4626] [--network ...] [--desk <address>]
    specfirst desk status [<id>] [--limit 20] [--network ...] [--desk <address>]
    specfirst desk withdraw --to <address> [--network ...] [--desk <address>]
    specfirst worker [--network monad-testnet] [--subject-rpc <url>] [--poll 15] [--once] [--runs 16] [--block-lag 10]
                     [--check-timeout 600] [--report-base-url <url>] [--allow-unknown-proxy] [--desk <address>]

The desk address defaults to `SPECFIRST_DESK_<chainId>`. `desk deploy` signs with `DEPLOYER_PRIVATE_KEY` (the owner), takes the registry from `SPECFIRST_ATTEST_REGISTRY_<chainId>`, makes the address of `ISSUER_PRIVATE_KEY` the worker unless `--worker` is given (with a warning when the worker is not a registry issuer or not that key), defaults to a fee of 0.1 MON and a timeout of 21600 s (6 hours), and prints the address and its `export` line as soon as the deploy is mined. `desk request` pays from `REQUESTER_PRIVATE_KEY` and refuses to run without it, even on anvil. `desk withdraw` signs with the owner key and refuses when there is nothing earned to withdraw. `desk deploy` warns when the fee is 0. `desk status` only reads. Desk failures exit with 18.

## Subscriptions later (design note)
Monitoring (periodic rechecks of a subject) is not in this contract, and the desk cannot be changed after deployment. It fits best as a separate contract next to the desk, using the same registry and worker, so the request path keeps its small, tested surface:
- `subscribe(subjectChainId, subject, standardId, periods)` pays `pricePerPeriod * periods` into escrow; each period is a slot of fixed length.
- `fulfillPeriod(subId, period, attestationId)` by the worker earns one period's price with the same registry checks as `fulfill`, except that `issuedAt` must fall inside that period's window.
- A period that ends without a delivery becomes refundable to the subscriber after a grace time (the `refundExpired` rule per period), and `cancel` refunds the periods that have not started. The accounting invariant stays `balance == escrowed + earned - withdrawn`.
- The worker walks `subscriptionCount()` and `subscriptionOf(i)` with its own cursor, and can also recheck early when the subject's implementation key at the latest block differs from the last attestation (a proxy upgrade), which needs no contract support. Its progress goes to a separate file so `status.json` keeps this schema.
- A challenge window fits the same place: fees earned only after N hours without a revocation, which would let an independent checker's revocation return the fee.

## Consequences
- Anyone with testnet MON can get a vault checked and attested without us; we earn a fee only for delivered checks, and the requester gets it back when we cannot deliver or do not deliver in time.
- Operating cost is the worker's gas (recorded per request in `status.json`) and the suite's RPC load on the subject chain.
- The worker's honesty is not enforced onchain (see the trust model); it is checkable after the fact.
- The report URIs of worker attestations resolve only after `certs/checks` is pushed.
